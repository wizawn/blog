# 言零博客五类题材统一声线模板（v3）

为了避免写逆向时像极客、写部署教程时突然退化成官方说明书、写随笔时又变成矫情散文，本站常见的五类原创题材统一按以下叙事节拍与声线起草。无论哪一类，背后说话的人都是同一个：**爱较真、嫌麻烦、习惯先看抓包和源码、讨厌套话的一线安全研究员**。

---

## 题材一：客户端逆向 / 支付协议与风控分析
- **代表作**：`google-ai-ultra-trial/index.md`、`stripe-protocol-payment-automation-deep-dive-2026.md`、`google-play-ccmax-proration-vulnerability-2026.md`
- **标题写法**：`<具体动作或反常账单现象>：复盘/聊聊 <核心产品名 + 关键接口或机制>`（确保包含产品名与核心搜索词）。
- **章节推进**：
  - 开篇（不设 `## 前言`）：直接摆订阅档位价格、界面上的反常限制或圈子里流传的截图现象，点明底层猫腻在哪一环，顺嘴交代防扣费护栏（如测试卡限额、脱敏沙盒）。
  - `## 0x00`：拆开最核心的那一层协议/IPC 差异（拿真实抓包路径、枚举值或两套流向的小对比表说话，把外行常搞混的概念顺手拎清）。
  - `## 0x01 ~ 0x02`：还原把链路跑通时撞见的真实环境坑（模拟器架构、证书挂载路径、类型转换、时序竞态），用自然过渡句把三四个坑串起来配关键代码片段。
  - 最后一个 `0x0N`：站在服务端架构师角度给出两三条能真正焊死漏洞的代码/状态机校验逻辑（如核对 `priceAmountMicros`、绑死 `obfuscatedAccountId` / `appAccountToken`），写完即止，文末斜体交代脱敏。

## 题材二：CVE 漏洞复现 / 源码审计与应急响应实录
- **代表作**：`cve-2026-46331-pedit-cow.md`、`acg-faka-bepusdt-callback-forgery-analysis.md`、`nginx-lua-malware-incident-response-2026.md`
- **标题写法**：`<组件名 + 具体致命点或故障现象>（<CVE 编号或事件定性>）`。
- **章节推进**：
  - 开篇（如漏洞已修，顶部可放一行简短 `> 修复说明：...`）：直接给受影响版本范围、披露时间与最扎眼的故障/利用表象（如“没见着半个 WebShell 库存却空了”、“改个大写 `/API/` 直接打穿后台”）。
  - `## 0x00`：直奔源码行级病根或日志时间线（放出十来行关键成因代码或请求特征，一眼点破哪两个函数的假设打架了，绝不抄大段八股文式的 CVSS 指标解释）。
  - `## 0x01`：本地回环靶机验证（强制绑死 `127.0.0.1:`，交代清楚判定穿透的真实状态码或回显特征）或顺藤摸瓜挖持久化后门。
  - `## 0x02`：止血加固与取证盲区（专挑网上错误配置来勘误，比如 Nginx `$uri` 已折叠导致正则失效、`rewrite` 跳出 `allow/deny`、改完漏洞忘了轮换已泄露的 `jwt_secret_key`、半夜关 root 登录把自己锁死在门外），最后附官方公告链接收尾。

## 题材三：开源工具 / 模型服务端部署与排坑记录
- **代表作**：`openclaw-deploy-linux.md`、`moss-ttsd-16g-server-deployment-guide.md`、`windsurf-api-proxy.md`、`codex-tools-tutorial.md`
- **标题写法**：`<在什么环境跑通什么工具> 的折腾/排坑记录：<两三个具体硬坑>`（严禁写“超详细保姆级教程 / 2026 终极版”）。
- **章节推进**：
  - 开篇：先吐槽两句网上二传手教程里害人不浅的典型错误（比如把 HTML 网页喂给 `bash`、往 `/tmp` 里 `git clone`、教人全局关杀毒或裸开 `0.0.0.0` 弱口令），再点明本文实测跑通的硬件/系统基线与合规边界。
  - `## 0x00`：前置门槛准备（Swap 交换空间、精确到小版本的 Node / Python 门槛、非 root 普通运行用户、代理验证命令）。
  - `## 0x01 ~ 0x02`：核心安装与配置文件落盘（给出可直接复制、语法无误且默认绑死 `127.0.0.1` 回环口的配置块，顺带讲清为什么某个参数不能照抄旧模板）。
  - 最后一个 `0x0N`：后台常驻守护（systemd / LaunchAgent / PM2 / tmux 的防死循环与防孤儿进程细节）、SSH 隧道本地访问与两三个最高频报错速查，干净收工。

## 题材四：高频报错速查 / 配置切换短篇（1000 ~ 1800 字）
- **代表作**：`codex-common-errors.md`、`codex-reconnecting-5-times.md`、`codex-stuck-troubleshooting.md`、`codex-official-relay-switch.md`
- **标题写法**：直接用用户在搜索框里敲的原话做标题，如 `Codex 提示 Reconnecting 5 次，怎么处理？`、`Codex 常见报错怎么处理：capacity、429、503、usage_limit 一次看懂`。
- **章节推进**：
  - 开篇两段直接安抚焦虑、打破常见误判（如“跳满 5 次只是默认重连配额用光了，跟封号没关系”、“别一上来就删 `~/.codex` 把历史全扬了”）。
  - 中间给一张干净利落的“状态码 -> 真实原因 -> 动作”对照表，或按从轻到重的顺序用自然段写出四五步分流排查法（先备份、每次只改一个变量、彻底退出重开客户端验证）。
  - 结尾交代如果真要提工单需要记下哪几项信息、外发前必须把哪些敏感文件（`auth.json`、API Key、业务代码）抹干净，附上两三个官方文档链接即止。

## 题材五：技术人深夜随笔 / 公告短文
- **代表作**：`404-not-found.md`、`502-bad-gateway.md`、`connection-reset.md`、`hello-world.md`
- **声线铁律**：克制、冷幽默、点到为止。拿真实存在的协议握手、Nginx 错误日志或 `iptables` 规则做比喻时，**技术细节本身依然要绝对准确**（不能写出语法报错的命令或级别写错的 Nginx 日志），情绪藏在终端命令和状态码背后，绝不煽情喊口号。
