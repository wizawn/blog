2026 年 9 月中旬那阵子，用 ChatGPT 和 Codex 干活的人几乎都在吐槽同一件事：头一天还能顺顺当当做完跨文件重构的个人 Pro 账号，第二天喂一模一样的上下文就开始丢三落四；Codex 的云端任务动不动弹 `overloaded, please try again later` 排队半小时；有些号刚发没几条请求，离套餐速率上限还差得远就先吃了 `429 Too Many Requests`。

那几天社区里有人顺着流量往下扒，摸出了一套跟 `current_turn_state` 有关的调度凭据机制，还顺手搓出了本地续期套件 `codex-state-kit`。因为这套东西建立在黑盒抓包观测之上，OpenAI 服务端随时可能改规则，趁手头日志还在，把它的工作机制、四个组件的配合方式以及容易踩空的协议细节记一笔，顺带把"跑出来的事实"和"没法打包票的推测"分清楚。

## 0x00 `292` 签发与 `312` 撤销：一小时通行证也会被中途收走

动手聊机制之前，先把几个经常被混着叫的接口路径摆清楚。大家嘴上习惯统称"chat completion 接口"，但实际上 ChatGPT 网页端走的是 `/backend-api/conversation`，拿订阅账号登录的 Codex 客户端走的是 Responses 风格的 `/backend-api/codex/responses`，而本地反代工具对外暴露给客户端的往往是兼容标准 SDK 的 `/v1/chat/completions` 或 `/v1/responses`。

翻看 `codex-state-kit` 的运行日志，整套逻辑围着上游返回的两个特殊标记转，工具里把它们记成 `292` 和 `312`。单看流出的运行日志截图，其实还不能百分百咬死它们到底是字面意义上的底层 HTTP 状态行，还是 SSE 事件流 / 响应体里的自定义状态字段：毕竟按 RFC 9110 §15 的规矩，标准 HTTP 客户端和中间代理遇到不认识的 `2xx` 会退化成 `200` 处理，遇到没带 `Location` 头的陌生 `3xx` 甚至可能按重定向类去解析，所以把它们当成上游响应里嵌着的一对调度信号来理解更稳妥。

先看 `292` 信号。满足特定前置条件时，上游响应会带回一个叫 `current_turn_state` 的凭据字段。从守护进程 `keeper` 打出来的倒计时看，这份凭据的名义寿命大约是 1 小时（刚落盘时显示剩余约 59 分钟）。后续发出去的请求只要夹带着还在有效期内的 `current_turn_state`，实测很少再撞上 `overloaded` 排队，写起长代码来上下文也稳当得多。日志里偶尔还会蹦出 `292 / 10 块` 这样的字样，里面的"10 块"看着像某种配额分片或并发槽位计数，目前还没有完整抓包能定死它的确切含义。

再看让人防不胜防的 `312` 信号。拿到 `292` 绝不意味着接下来这一个钟头就能高枕无忧了：哪怕你手里的 `current_turn_state` 倒计时还剩四十多分钟，上游在使用过程中照样会主动下发 `312`。一旦撞上 `312`，手头那串凭据当场作废，再接着往下发请求又会掉回容易过载或回答缩水的状态。

把这两个信号拼到一块儿，平时大家抱怨的"模型一阵聪明一阵犯傻"就很好解释了。服务端一直在动态重算会话调度资格，你聊着聊着突然觉得模型像换了个小号，可能是 1 小时 TTL 自然到期没续上，也可能是半道被 `312` 提前收走了通行证，站在前端界面上看过去表现一模一样。

## 0x01 什么条件下更容易拿到 `292`

这部分得实话实说：服务端内部到底按哪几条权重给 `292`，外面谁也没见过源码清单。从 `codex-state-kit` 的默认动作和大家跑出来的反馈看，工具作者最看重的变量是出口 IP 类型。

每次去采 `292` 的时候，守护进程都会先调 Clash 的控制接口把出口切到住宅宽带或原生 IPv6（实测记录里挂美国住宅宽带发第一条请求就顺利吐出了 `292`），等把 `current_turn_state` 写进本地凭据文件，立马切回日常用的香港专线接着干活。

但这并不代表"只要挂上美国真家宽就百发百中"，也不能反过来断定"机房 IP 绝对拿不到"。除了出口网络的 ASN 信誉之外，订阅档位（实测跑在月费 $200 的个人 Pro 20x 号上，Plus 或 Business 档门槛是否一致没人做过严格对照）、模型标识（工具配置里死死锁在 `gpt-6-astra` 同模型采集与调用，跨模型混用大概率不认）、请求频率与账号自身的历史风控评分，外加美西工作高峰期的上游实时负载，全都在一块儿起作用。

倒是有个现象在当时的实测里非常明确：在住宅 IP 上采下来的 `current_turn_state`，切回香港低延迟专线之后继续用依然有效。说明至少在那个时间点，服务端要么没给这份 state 做死板的单 IP 绑定，要么绑定的粒度放得相当宽。

## 0x02 四个本地组件怎么配合续期

对比那阵子社区里常见的几种土办法，差距还是挺明显的：

| 应对路子 | 具体做法 | 实际痛点 |
|---|---|---|
| 盲换代理节点 | 觉得变笨了就手动切条线路碰运气 | 纯凭手感，换完该排队照样排队 |
| 频繁重开新对话 | 关掉老窗口重新触发一轮会话分配 | 攒了半天的代码上下文全丢了，新窗口也不保准能分到好资源 |
| 多开 Pro 账号轮换 | 备两三个 Pro 号轮着顶 | 成本太硬，一个号一个月就是 $200 |
| 错峰熬夜干活 | 特意避开美西白天的工作高峰期 | 作息完全颠倒，赶急活时根本不现实 |
| 本地注入 `292` state | 守护进程切线采凭据，本地代理自动夹带并盯防 `312` | 需要自备住宅代理出口，还得改客户端本地路由配置 |

在 `codex-state-kit` 里，整套活儿被拆给了四个本地组件打配合：`Clash` 负责听指挥在"住宅/原生 V6"与日常专线之间来回切路由；`keeper.py` 作为后台守护进程盯着凭据寿命（日志落在 `~/codex-state-kit/logs/keeper.log`）；定制改过的 `gpt-load`（监听 `127.0.0.1:3001`）配合桌面端拦截层 `inject_proxy` 负责在每次转发请求时从磁盘读出最新的 `current_turn_state` 塞进去，同时瞪大眼睛看上游响应里有没有冒出 `312`。这里顺嘴提一句，开源原版的 `gpt-load` 只是一个多 Key 轮询网关，并不会自己往请求体里塞 `current_turn_state`，注入动作靠的是定制补丁或前置的 `inject_proxy`。

续期走的是双线触发，哪条先撞线就按哪条跑：平时每轮检查如果发现 TTL 剩余不到 5 分钟就提前去换新凭据；要是半途被代理抓到了 `312`，马上通过本地信号唤醒 `keeper` 立即重采，不等 45 秒轮询慢吞吞走完。

把 `keeper` 的核心循环用 Python 伪代码还原出来（顺手补上原版思路里漏掉的 `try/finally` 路由回切和失败退避 `sleep(45)`，不然哪次网络抽风抛了异常把全局流量死锁在慢速家宽上，或者采不到 `292` 时无间隔死循环狂刷上游把 Clash 切炸就乐子大了）：

```python
while True:
    remaining = state_expires_at - now()
    # 阻塞等待代理发来的 312 事件，最长等 45 秒；一旦捕获 312 立刻唤醒
    got_312 = wait_for_312_event(timeout=45) if remaining > 300 else check_312_signal()

    if remaining > 300 and not got_312:
        continue

    if got_312:
        log("捕获 312 撤销信号，立即重采 292")

    clash.switch_to("住宅/原生 V6")
    need_backoff = False
    try:
        resp = send_probe_request(model="gpt-6-astra")
        if has_292_state(resp):
            save_turn_state(resp.current_turn_state)
            clear_312_signal()
            log("292 凭据更新完成")
        else:
            log("本轮未拿到 292，45 秒后重试")
            need_backoff = True
    finally:
        # 无论成功还是报错，确保把路由切回日常工作专线
        clash.switch_back()

    if need_backoff:
        sleep(45)
```

到了 Codex 客户端这一头，有个不能含糊的配置细节。原帖说"除了把 Base URL 指到本地代理不用改任何配置"，这话其实把模式切换给说漏了：一旦你把 Codex 指向 `http://127.0.0.1:3001/v1` 并填上 `~/codex-state-kit/config.json` 里的 `gptload.access_key`，Codex 就跳出了默认零配置直连官方后端的订阅路径，改走 `config.toml` 里的自定义 `model_providers` 模式（写法可以参考站内另一篇[官方登录与中转服务切换笔记](/posts/codex-official-relay-switch/)），模型名也得老老实实对齐成采集用的 `gpt-6-astra`。

## 0x03 躲不开的空窗期与安全红线

哪怕把上面整套链路全跑顺了，它也远谈不上什么一劳永逸的神药。

最棘手的是续不上的空窗期。万一你写代码写到一半突然吃了个 `312`，偏偏那几分钟住宅代理掉线或者 OpenAI 全局算力彻底见底，`keeper` 连试几轮都采不回新的 `292`，在采回来之前就只能干瞪眼受着。而且 `current_turn_state` 是跟具体账号会话绑定的，A 号采出来的 state 塞给 B 号没用，手里好几个号就得给每个号单独挂一套守护进程。再加上所谓"降智"本来就掺着不少主观体感，社区里只有"挂上之后 overload 确实少见了"的经验反馈，并没有严格双盲的对照测试数据，心里别把它捧得太玄乎。

最后一定把凭据安全和合规账算清楚。落在本地磁盘上的 `current_turn_state` 以及配套配置里的会话 Token 全是敏感凭据，文件权限务必收紧到 `chmod 600`；如果你想图省事跑社区里别人封装好的第三方实现（比如 GitHub 上的 [`gylive/ccodex-sleep-state`](https://github.com/gylive/ccodex-sleep-state)，注意仓库名开头确实是两个 `c`），动手喂账号进去之前先把它的源码从头到尾翻一遍，确认没有暗地里往外发凭据的逻辑。至于借住宅代理切线加手工注入服务端状态字段去绕调度，无疑踩在 OpenAI 服务条款的红线边缘，拿自己的长期主力号去试之前先掂量清楚封号风险。
