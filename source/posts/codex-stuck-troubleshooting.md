Codex 用久了偶尔会碰上敲完回车石沉大海、按钮没反应或者桌面端窗口卡白的情况。很多人第一反应是卸载重装，甚至一着急直接把整个 `~/.codex` 目录删了，结果本地攒的会话记录全打了水漂。其实顺着从轻到重的顺序排一遍，绝大部分卡死都能在不丢历史的前提下救回来。

## 0x00 先分清三种看着很像的"卡住"

动手之前先瞄一眼界面角落：很多时候它压根没死，只是刚才要跑一条带写文件或联网操作的命令，正停在权限审批框那儿等你点允许或拒绝呢，点完立马就接着往下走了。

如果界面上能清楚看到 `Reconnecting`、`capacity`、`429` 或者 `503` 这些字样，那属于连接重连或上游限流过载（连续撞上相同的 `429`/`503` 记得停手按 `Retry-After` 退避，别连着狂点延长限流），直接对照 [重连 5 次排查](/posts/codex-reconnecting-5-times/) 和 [常见报错表](/posts/codex-common-errors/) 处理就行。排除了等审批和网络限流，剩下的才是真正的本地界面或会话异常。

## 0x01 从轻到重按五步定位

第一步先把输入框里刚敲好还没发出去的一大段话全选复制存好，免得一会儿重启应用白敲一遍。

第二步新开一个独立的系统终端窗口探探底，跑一下 `pwd`、`df -h`（如果当前目录是 Git 仓库再顺手敲个 `git status`，非 Git 目录跳过这句）。我真碰见过好几回错怪了 Codex 的现场：查到最后其实是宿主机磁盘 100% 写满了、外接移动硬盘休眠卡死了 I/O，或者仓库里残留着 `.git/index.lock` 让后台每条 git 命令都直接报错退出。连普通终端敲命令都卡的话，先把本机磁盘和权限收拾利索再说。

第三步开一个干净的新会话，发一句最简单的 `hi` 做对照。要是新会话秒回，唯独刚才那个老会话一发就转圈，基本就能断定是老会话上下文叠得太厚了，或者前一步某个工具调用吐回了几十兆脏日志把渲染器撑爆了；反过来要是新会话发 `hi` 也一样卡死，那就不是单个会话的锅，回头按 `0x00` 查网络、系统时间、代理和官方状态页。不过要注意，新会话能正常说话，不代表刚才老会话里挂起的后台任务已经跑完了，切换前心里要有数。

第四步把客户端升到最新稳定版，然后彻底退出重开。桌面端记得从菜单栏或托盘选完全退出（macOS 按 `Cmd + Q`，光点左上角红叉只是关了窗口），CLI 确认后台没有残留进程后再重新打开试一次。

第五步针对"只有某一个项目一进就卡、进空文件夹却丝滑正常"的情况，重点查那个项目底下是不是躺着几百兆没进 `.gitignore` 的日志或构建产物、符号链接死循环，或者挂掉的项目级 MCP 脚本。还是抓不到原因的话，再去翻本地日志按"打开应用 -> 进目录 -> 发短消息 -> 卡住"记下时间线：macOS 桌面端日志按日期落在 `~/Library/Logs/com.openai.codex/YYYY/MM/DD`；CLI 与 TUI 日志默认目录在 `$CODEX_HOME/log`（即 `~/.codex/log`，Windows 对应 `%USERPROFILE%\.codex\log`），如果想让它落盘输出纯文本的 `codex-tui.log`，需要先在 `config.toml` 里显式写上 `log_dir = "~/.codex/log"` 再复现一次；会话历史则在 `$CODEX_HOME/sessions`。

排查全程都别去删 `auth.json` 和项目源码。真要找 [OpenAI 帮助中心](https://help.openai.com/) 提工单（官方排障说明见 [Codex Troubleshooting](https://developers.openai.com/codex/app/troubleshooting)），记得附上完整报错、客户端版本、模型名、带时区的发生时间和请求 ID，发截图或日志前一定先把里面的业务代码、本地路径、邮箱、Token、API Key 和代理口令抹干净。
